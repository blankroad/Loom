# TEST 기획 브리프 (v2.0 신규, EXPLORE 팀 담당) — TC·자연어 기반 통합 테스트

먼저 읽기: `02-core-principle.md`, `00-master-plan.md`(§2.3 **C7·C8** 중심, D12·A15), `explore/plan.md`의 교차 러너 절, 각 팀 `plan.md`의 스킬·시나리오 절.

## 사용자 의도 (원문 요지)
"각 모듈을 혼합하여 사용하는 TC 기반 혹은 자연어 기반 통합 테스트도 가능해야 함. 그래서 스킬로 빼는 것임. 에이전트가 붙어 있으면 TC를 위한 코딩을 안 해도 되기 때문."
즉 **사람은 TC를 자연어나 표로 쓰고, 에이전트가 스킬과 `loom` 명령으로 UART·CAN·UDS·LA·DLT 등을 섞어 실행**한다. 사용자는 실행을 UI에서 실시간으로 보고 개입한다.

## 범위
1. TC 형식: 자연어 자유 서술부터 반구조 표(전제·장비·환경·단계·기대 결과·합격 기준)까지. 기존 사내 TC(엑셀·문서) 가져오기 고려.
2. 테스트 세션: `loom test start/step/verdict/attach-evidence/end` 같은 CLI(코어 부분은 CORE와 `_xteam/core-test.md` 합의), 세션 시작 시 일괄 사전 승인(R2/R3), 단계 마커가 모든 도메인 이벤트 타임라인에 찍힘.
3. **증거 기반 판정 (환각 방지)**: 단계 판정은 이벤트 seq 범위·신호 값·응답 바이트 등 증거를 인용해야 하고, Loom이 인용 증거가 실제로 있고 기대와 일치하는지 검증. 증거 없는 PASS 금지. 애매하면 `inconclusive`.
4. 보고서: HTML(UI에서 열람) + JUnit XML 등, 기록 구간 링크.
5. 회귀 재실행: 에이전트 실행 기록을 결정적 시나리오(`loom run`)로 고정해 에이전트 없이 재실행(선택), 둘의 관계.
6. `loom-test` 스킬 설계: TC 해석 규칙, 단계 실행·대기·판정·보고 규칙, 실패 시 행동(STOP·복구 송신), 사람에게 묻는 조건.
7. UI 테스트 실행 화면 요구(현재 단계, 실시간 증거, 판정, 사람 개입) — UI 팀에 `_xteam/ui-test.md`로 전달.
8. 예시 TC 3개 이상(UART 부팅 + CAN 신호 + UDS DTC 혼합 등)과 시뮬레이션 위 E2E 시나리오.
