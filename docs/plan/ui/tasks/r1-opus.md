# R1 — ui-opus 지시

먼저 `docs/plan/ui/tasks/r1-common.md`를 읽고 그대로 따른다. 출력: `docs/plan/ui/r1-opus.md` (한국어, 15절 + §0 핵심 루프).

## 당신의 관점 (무게를 둘 곳)

**아키텍처 · 사용자/에이전트 UX · 패널 프레임워크 설계 · 안전 UX.** 라이브러리 세부 벤치마크는 ui-sol이 맡으니, 기술 선택은 요구사항과 판단 기준 중심으로 쓰고 후보만 제시해도 된다.

1. **화면 설계(와이어프레임 필수)**: 공통 셸 전체 화면, UART 터미널 패널, CAN Trace+Graphics, UDS 콘솔, 승인 대기열/승인 모달, 테스트 실행 화면, STOP 후 상태("STOP — 출력 유지 중" + 복구 송신 1키). M1 화면과 이후 화면을 구분.
2. **사용자 개입 UX**: 사용자가 UI에서 송신·입력·take-control·hold·승인·거부·STOP·비상 OFF를 하는 흐름. 에이전트와 사용자의 입력이 섞일 때 화면 표시(출처 배지, 입력권 lease 표시, `others_since_last`와의 대응). 쓰기 상태 단계(D4/A14: requested→accepted→sent→confirmed…/outcome_unknown)를 행 하나에서 점진 갱신하는 표시 규칙.
3. **에이전트 자기 승인 차단 UX**: 브라우저 자동화로 승인 버튼을 누르는 시나리오를 구체적으로 분석하고 완화안 2~3개를 비교·추천.
4. **패널 프레임워크**: `registerPanel` 형태의 API 초안(TS 시그니처), 패널 manifest(구독 토픽·필요 RPC·위험 동작·기본 레이아웃), 도메인 팀이 채울 **패널 명세 템플릿**(`_xteam/<comp>-ui.md`에 쓸 양식). 패널이 직접 장치를 열 수 없고 데이터는 오직 코어 구독/질의로 — 이 불변식을 API 수준에서 강제하는 방법.
5. **상태·데이터 흐름 구조**: WS 연결 1개 다중화, 구독 관리자, 도메인별 스토어/링 버퍼, 렌더 스케줄러(rAF·20 Hz 상한), 우선 제어 이벤트의 별도 경로. 구성도(ASCII).
6. **레이아웃·작업 공간**: 저장 형식, 에이전트가 레이아웃/패널을 열어 사용자에게 보여 주는 방법(예: `loom ui open can.trace --filter ...` — 에이전트가 사용자 화면을 "가리키기"), 여러 브라우저 탭/사용자 동시 보기.
7. **테스트 실행 화면**: TEST 기획 브리프(`docs/plan/test/brief.md`)를 읽고 현재 단계·실시간 증거·판정·사람 개입 화면 요구를 정리.
8. **M1 정의와 작업 분해**: M1 수용 기준(자동 시험 가능 형태), 작업 단위별 담당 추천(Opus/Sol)과 의존성(CORE stub 등).
9. 도메인 팀·CORE 팀에 요청할 것 목록(§15).
