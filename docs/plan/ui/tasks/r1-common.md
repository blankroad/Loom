# UI 팀 R1 공통 지시 (ui-opus, ui-sol 둘 다 읽기)

작성: ui-lead, 2026-11-10. 모든 문서는 **한국어**로 쓴다.

## 0. 이 팀이 하는 일

Loom v2.0에서 사용자 화면은 TUI가 아니라 **Loom UI 앱(웹, `loomd`가 127.0.0.1로 제공)** 이 1차다(마스터 §2.3 C6). UI 팀은 공통 셸·패널 프레임워크·`loom.viz`·1차 도메인 패널 구현을 소유한다. 도메인 팀(UART/CAN/UDS/EXPLORE)은 패널 **내용 명세**와 데이터 질의를 소유하고, CORE 팀(Rust `loomd`)은 IPC·이벤트 허브·스키마를 소유한다.

핵심 한 줄: **에이전트가 장치에 쓰고 읽는 바로 그 데이터가 같은 순간 UI에 보이고, 사용자는 UI에서 직접 송신·입력·승인·STOP으로 개입한다. 에이전트만 보는 숨은 데이터는 없다.**

## 2. 산출물

- 각자 `docs/plan/ui/r1-<이름>.md` 하나 (ui-opus → `r1-opus.md`, ui-sol → `r1-sol.md`).
- 형식: `00-brief.md` §4의 **15절 전체** + 맨 앞 `## 0. 핵심 루프` 절. 각자 관점(아래 개별 지시)에 무게를 두되 15절은 모두 채운다(약한 절은 짧게).
- 분량 목표 600~1,000줄. 사용량 한도가 있으니 같은 내용 반복 금지, 표·목록 위주.
- 주요 화면은 **ASCII 와이어프레임**으로.
- 사실(버전·라이선스·성능 수치)은 출처(URL, 패키지 레지스트리, 소스 파일, 직접 측정)를 붙인다. 확인 못 한 것은 "미확인"으로 표시.

## 3. 계획서가 반드시 답할 질문

### 핵심 루프 (02 원칙 체크리스트)
- `## 0. 핵심 루프` 표: 직접 접근·읽기·쓰기·사용자 실시간 표시가 UI 쪽에서 각각 무엇으로 구현되는지 (UI는 장치를 직접 열지 않는다 — 그 사실과 대신 무엇을 보장하는지).
- 종단 간 시나리오 1개 이상: "에이전트가 `loom uart send` / `loom can send` / `loom uds read-did` → 장치 응답 → UI 패널에 몇 ms 안에 → 사용자가 UI에서 어떤 입력으로 개입" — 구체 명령, 화면, 이벤트 흐름.
- 지연 목표 (장치→화면 p95: UART 100 ms, CAN 200 ms, UDS 100 ms; 플롯 250 ms)를 **브라우저 쪽 예산으로 분해**(배치 대기·전송·디코드·상태 반영·렌더). 브라우저에서 지연을 어떻게 재고 `lag`로 표시하는지(브라우저 시계와 데몬 mono 시계 정렬 방법 포함).
- 고부하(CAN 버스 100%, UART 폭주, 연속 0x78)에서 화면이 멈추거나 거짓말하지 않는 방법: `display.gap`, `LIVE/LAG/STALLED/LIVE-DEGRADED`, 다운샘플 표시, 우선 제어 큐 이벤트(응답·승인·STOP)는 절대 묻히지 않음.
- M1 = 걷는 뼈대: 시뮬레이션 위에서 셸 + 최소 패널(UART·CAN·UDS)로 "에이전트 송신 → 화면 → 사용자 개입" 시연. 멋진 기능은 M1 이후.
- 사용자 UI는 에이전트 세션과 분리되지 않음: UI를 언제 열어도 snapshot + live로 같은 스트림.
- 원칙에 기여하지 않는 기능은 "후순위"/"비범위"로 명시.

### UI 고유
- 앱 형태: 웹 SPA 정적 파일을 `loomd` 바이너리에 내장(오프라인 벤치 PC — CDN 금지)할지, Tauri 셸은 언제·왜. 원격 보기(Windows/Linux 벤치 PC의 UI를 macOS에서) 시 인증·전송.
- 인증: 웹 일회성 bootstrap → HttpOnly 쿠키(D2), viewer role, origin=user는 서버가 연결 자격으로 부여.
- **에이전트 자기 승인 차단**: R3/R4 승인은 뷰어 전용인데, 에이전트가 브라우저 자동화 도구(Playwright, ego-browser 등)로 UI를 열어 승인 버튼을 누를 수 있다. 위협 모델(D6: 실수 방지, 악의적 우회 방지 아님) 안에서 어떤 완화를 둘지(예: 승인 코드 입력, OS 수준 사용자 존재 확인, 에이전트가 쓰는 쿠키/세션과 분리, 감사).
- 데이터 계약(CORE와): 구독·질의·쓰기 RPC 사용 방식, 고속 데이터 전송 형식(JSON vs 바이너리/열 단위), 스키마 → TS 타입 생성, 대용량 질의(HTTP GET / `raw_ref`).
- 패널 프레임워크: 도메인 패널 등록 방식(정적 번들 vs 동적 로드), 패널 ↔ 코어 계약(구독·질의·쓰기 훅), 패널 명세를 도메인 팀이 쓰는 템플릿.
- 공통 셸: 레이아웃(분할·저장·에이전트가 `--layout` 지정), 전역 STOP·비상 OFF, 승인 대기열, env 배지(`vehicle`), 연결·gap·LAG, 기록 탐색·재생, 마커, 테스트 실행 화면(TEST 기획과 합의), Activity(에이전트 행동 타임라인).
- 1차 패널: UART 터미널(xterm.js, 원시 키·Ctrl-C, 입력 중재 InputArbiter와 입력권 lease), CAN Trace/Graphics/IG/Data, UDS 콘솔(점진 갱신 트랜잭션 표), LA 레인(캡처 후 표시), DLT, `loom.viz`(데이터만 주면 렌더링 — 파일·라이브).
- C2(메모리): 브라우저 쪽도 링 버퍼 상한·가상 스크롤·오래 켜 둔 탭의 메모리 증가 상한(24 h soak에 UI 포함 여부).
- 테스트: HW 없는 CI에서 UI 수용 시험(브라우저 E2E, 지연 측정, 고부하 정직성 시험), 3-OS.
- TUI의 위치(보조): 무엇을 남기고 무엇을 안 만드는지.

## 4. 규칙

- 쓰기 허용: 자기 출력 파일(`docs/plan/ui/r1-<이름>.md`)과 `spikes/ui/<이름>/` 아래만. 다른 팀 폴더·`_xteam/`은 읽기만(리드가 조율 파일을 쓴다).
- 제품 구현 금지. 스파이크는 계획 근거용 짧은 코드만.
- 전역 설치 금지(npm -g, brew, cargo install 등). Node 패키지는 `spikes/ui/<이름>/` 안 로컬 `node_modules`. Playwright 브라우저가 필요하면 `PLAYWRIGHT_BROWSERS_PATH=spikes/ui/<이름>/.browsers` 로 로컬에 받는다. 사용자 설정 파일(~/.claude, ~/.codex 등) 수정 금지.
- 다른 에이전트(다른 워크스페이스 포함)에게 herdr 명령 보내지 말 것.
- 끝나면 파일 저장 후 짧게 "완료: <경로>"라고만 답한다.
