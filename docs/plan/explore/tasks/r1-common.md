# R1 공통 지시 — explore (explore-opus, explore-sol 둘 다 읽을 것)

당신은 Loom 프로젝트 **④ 탐색(Explore)** 컴포넌트의 계획 워커다. 리드는 explore-lead.
목표: UART / CAN / UDS 외에 Loom에 넣을 만한 **추가 장비·프로토콜 컴포넌트**를 찾아 평가하고, 상위 후보에 간이 계획을 세운다.
**계획 단계다. 구현 코드는 쓰지 않는다.** (사실 확인용 짧은 스파이크만 `spikes/explore/` 안에서 허용)

## 먼저 읽을 것 (순서대로)
1. `docs/plan/02-core-principle.md` — **최우선 판단 기준**. 에이전트가 장비에 직접 접근 → 읽기 → 쓰기 → 사용자가 같은 데이터를 같은 순간 라이브로 봄(출처 agent/user/device, 사용자 개입 가능). 이 루프가 성립하고 가치가 큰 것만 높게 평가한다. 파일 분석 도구 같은 건 낮은 순위.
2. `docs/plan/00-brief.md` — 공통 브리프, 특히 §3 공통 아키텍처 계약(데몬 장치 소유, 로컬 IPC, `loom <domain> <verb>` CLI, 출처 표시, 공통 이벤트 레코드, loom.viz, 시뮬레이션 필수, 안전, 스킬 패키징).
3. `docs/plan/explore/brief.md` — 이 컴포넌트 브리프 (후보 씨앗, 산출물 5개 항목).
4. 중복 회피용(읽기만): `docs/plan/uart/`, `docs/plan/can/`, `docs/plan/uds/` 의 brief.md와 진행 중 초안(r1-*.md, plan.md가 있으면), `docs/plan/_xteam/*.md`.
5. 사용자 맥락 참고(읽기만): `~/Desktop/01_PROJECT/dlt-wrapper` (COVESA DLT C 래퍼. README와 docs 정도만 훑어 사용자가 DLT를 어떻게 쓰는지 파악).

## 사용자 맥락
- 차량용 임베디드/진단 개발자로 보임 (UART 콘솔, Vector/PCAN CAN, DoIP/CAN-TP UDS, DLT 로깅).
- 주 개발 머신 macOS, 실제 HW는 Windows 가능성.
- 이 팀은 기존 세 팀의 범위를 바꾸지 않는다. 겹치면 "기존 팀 범위에 흡수" 또는 "공통 계약 변경 요청"으로 적는다.

## 산출물 구조 (한국어, 절 번호와 제목 유지)

```
0. 요약 (결론 먼저: 상위 추천 3~5개와 한 줄 이유, 착수 순서)
1. 핵심 루프 적합성 기준표
   - 4요소(직접 접근 / 읽기 / 쓰기 / 실시간 표시) 각각의 판정 기준(○ 성립 / △ 부분 / ✗ 불성립)을 구체적으로 정의
   - 점수화 방법(가중치 포함)과 "핵심 루프 불성립이면 상위 추천 불가" 같은 탈락 규칙
2. 범위 / 비범위 (이 팀이 다루는 것, 기존 세 팀에 남기는 것)
3. 후보 전체 평가표 (최소 15개 후보. 브리프 씨앗에서 빼거나 더할 것)
   - 열: 후보 / 사용자 가치 / 핵심 루프(4요소 각각 ○△✗) / 구현 난이도 / Python 라이브러리 성숙도(실제 확인: 패키지명, 최신 버전, 마지막 릴리스 날짜, 라이선스) / HW 확보 난이도 / macOS·Windows 지원 / loom.core 재사용도 / 기존 3팀과 중복 / 총점
   - 표 아래 후보별 짧은 근거(2~5줄). 탈락 후보는 탈락 이유.
4. 상위 3~5개 추천 — 후보마다 소절, 각 소절에 다음을 모두:
   a. 핵심 루프 표 (4요소가 이 도메인에서 각각 무엇: 명령, 데몬 구성요소, 뷰어 화면)
   b. 종단 간 시나리오 1개 이상 ("에이전트가 X를 보냄 → 장비가 Y로 응답 → 사용자 화면에 Z가 몇 ms 안에 뜸 → 사용자가 W로 개입 → 에이전트가 그 개입을 origin=user로 읽음"을 구체 명령과 화면으로)
   c. 실시간성 목표치 (장비 이벤트 → 사용자 화면 지연) + 고부하 시 화면이 멈추거나 거짓말하지 않는 방법 (드롭 표시, 다운샘플링 명시, 기록은 무손실)
   d. CLI 초안 (`loom <domain> <verb> ...`, 경계 있는 동작: --timeout/--tail/wait-for, --json, 출력 상한) + 출력 예시
   e. 사용자 뷰 형태 (TUI/웹, 화면 구성 스케치, 사용자 직접 개입 수단)
   f. 주 라이브러리 (버전, 라이선스, 플랫폼 — 확인 근거)
   g. 시뮬레이션 백엔드 (HW 없이 4요소를 돌리는 방법)
   h. M1 걷는 뼈대 정의 (시뮬레이션 위에서 4요소 최소 동작, 수용 기준)
   i. 안전/가드레일 (위험 등급, 사용자 확인, dry-run, 한계값)
   j. 리스크
5. 공통 계약(loom.core, loom.viz)에 요구할 것 — 새 도메인을 쉽게 붙이는 **플러그인 구조 제안**
   (도메인 플러그인 인터페이스, 장치 백엔드 등록, 이벤트 레코드 확장, 안전 등급 레지스트리, 시뮬레이션 백엔드 등록, 뷰어 패널 등록, 스킬 패키징 규약, 패키지 배포 방식 예: entry points)
6. 추천 착수 순서와 이유 (기존 세 팀 M1 이후 어디에 끼우는지, 의존성)
7. 사용자에게 물어볼 질문 (각 질문에 기본값 제안 — 보유 장비 목록, 실차/벤치, OS 등)
8. 공통 계약 변경 요청 / 타팀 의존성
9. 핵심 원칙 체크리스트 자기점검 (02-core-principle.md의 6개 항목을 상위 추천 각각에 대해 [x]/[ ]와 해당 절 위치)
```

## 규칙
- 상대 워커와 상의하지 말고 독립적으로 쓴다 (다양성 확보). 상대의 r1 파일은 읽지 말 것.
- 파일 쓰기는 `docs/plan/explore/` 안(자기 출력 파일)과 `spikes/explore/` 안만. 다른 팀 폴더와 `_xteam/`은 쓰지 말 것.
- 전역 설치 금지 (pip install --user, brew 등). 필요하면 `spikes/explore/.venv` (uv 또는 python -m venv). 사용자 설정 파일(~/.claude, ~/.codex) 수정 금지. dlt-wrapper 폴더는 읽기만.
- 모르는 건 추측으로 단정하지 말고 "미확인"이라고 표시. 웹/문서/소스/PyPI로 확인한 사실은 출처(URL 또는 패키지 버전·날짜)를 적는다.
- 분량: 충분히 구체적으로 (대략 600~1100줄). 결론 → 근거 순서.
