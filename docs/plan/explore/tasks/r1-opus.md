## 당신의 관점 (무게를 더 둘 것)
- **핵심 루프 관점의 가치 판단**: 각 후보에서 "에이전트가 직접 만지고, 사용자가 같은 순간 보는" 그림이 실제 개발 업무(벤치 테스트, 부팅 디버깅, 진단, 캘리브레이션)에서 어떤 가치를 주는지. 차량 임베디드 개발자의 하루 업무 흐름에서 생각하라.
- **아키텍처**: 새 도메인이 데몬/IPC/이벤트 레코드/뷰어에 어떻게 꽂히는지. 도메인 플러그인 인터페이스(절 5)를 구체적으로 — 클래스/프로토콜 시그니처 수준 초안, 등록 방식, 공통 이벤트 레코드 `payload` 확장 규칙.
- **교차 기능**: 시나리오/테스트 러너(PSU 전원 사이클 → UART 부팅 로그 대기 → CAN 신호 확인 → UDS DTC 읽기), 모든 도메인 통합 타임라인, 세션 녹화·재생. 이들이 독립 컴포넌트인지 loom.core 기능인지 판단하고, 사용자가 시나리오 진행을 실시간으로 보고 중간에 개입(일시정지/중단/수동 단계)하는 UX.
- **사용자/에이전트 UX**: 화면 레이아웃 스케치, 출처 표시, 사용자 개입 수단, 에이전트 CLI 출력 형태.
- **스킬 설계**: 추천 도메인별 `.claude/skills/loom-<domain>/` SKILL.md 구성(짧게)과 references 목록.
- **안전 규칙**: 특히 위험한 도메인 — 전원공급기(과전압/과전류 한계, 출력 ON 확인), 디버그 프로브(실행 중 코어 halt, 메모리 쓰기, 플래시 erase), 릴레이(점화/전원 차단), XCP 캘리브레이션 쓰기. 위험 등급과 확인 규칙.
- 라이브러리 성숙도 열도 채우되, 깊은 사실 조사는 Sol 쪽이 맡으니 확신 없는 건 "미확인"으로 남겨도 된다.
