# v1.2 반영 작업 (사용자 답변) — 리드용

먼저 `00-master-plan.md` §2.2 **B1–B7**을 읽는다 (A·D보다 우선). 최우선 원칙(`02-core-principle.md`)은 그대로다: 에이전트가 장비에 직접 접근해 읽고 쓰고, 사용자는 같은 데이터를 실시간으로 보고 개입한다. 새로 넣는 CANoe 브리지·Saleae 경로도 이 원칙 기준으로 "사용자가 무엇을 언제 보는지"를 반드시 적는다.

## 공통 (모든 팀)
- 실 HW 호스트 = Windows x64 + Linux x64 (B1). macOS는 개발·시뮬레이션만. 실HW 체크리스트를 두 OS로 나눈다.
- vehicle 송신 기본 차단 폐기 (B4). 계획서에서 "vehicle tx deny", "vehicle = viewer 전용", "vehicle 송신 = R4" 표현을 찾아 B4로 고친다. 환경 배지 `env=vehicle` 상시 표시는 남긴다.
- 결정 기록 표에 "v1.2 사용자 답변 반영" 행을 추가한다. 큰 재작성 금지 — 바뀌는 절만 고친다.
- 사실 확인이 꼭 필요하면 워커 1명에게 짧은 확인 작업만 보낸다(사용량 한도 주의). 확인 못 한 것은 "미확인"으로 표시.

## UART
- B6: Linux 실 COM 체크리스트(권한·dialout, udev 시리얼 번호 별칭, USB 재열거 재연결, ttyACM DTR 리셋), Windows 체크리스트와 나란히.

## CAN
- B1: PCAN 실HW를 Windows(PCANBasic)와 Linux(SocketCAN `peak_usb`) 둘 다 M2 대상으로. Linux 인터페이스 up/비트레이트 설정을 누가 하는지(사람 사전 설정 vs 권한 헬퍼) 결정.
- B3: **`loom/canoe/` 브리지 v0를 P2(M2)에 추가** — Windows 전용, COM 전용 스레드, 측정 상태·시작/정지, 신호·시스템 변수 읽기/쓰기, 재연결. 브리지 위로 UDS 팀 `canoe` 백엔드가 올라갈 API(진단 요청 송신·응답 수신 경로)를 UDS와 `_xteam/canoe-bridge.md`에서 합의(CAN이 초안).
- B3: Vector 채널 공존 실측을 P3로 앞당긴다 (CANoe 측정 중 python-can `vector` 동시 열기, init access 없음, 수신·송신 가능 여부). 실패 시 대체 경로 = 브리지.
- CANoe UI에서 사람이 보낸 트래픽의 표시 규칙(`external:canoe`)을 트레이스·웹 뷰에 반영.

## UDS
- B3: **백엔드 `canoe` 추가** (Windows): CANoe에 설정된 진단 기술·seed-key·DoIP/CAN-TP를 사용. 위험 분류·승인·감사는 Loom 파이프라인 그대로. 요청·응답 이벤트를 Loom 뷰어에 발행. 기본 경로 규칙: CANoe 측정이 켜져 있으면 `canoe`, 아니면 자체 스택(Linux는 항상 자체 스택). 진단 DB: CANoe 쪽 이름(DID·루틴 이름)을 가져와 표시할 수 있는지 검토.
- B3: 자체 스택(DoIP, CAN-TP)은 필수 유지. CANoe가 Vector 이더넷 인터페이스를 쓰는 중일 때 자체 DoIP(PC NIC)와의 충돌 가능성을 리스크로 적는다.
- B4: A10 폐기 반영 — vehicle에서도 bench와 같은 규칙.
- `_xteam/canoe-bridge.md`에 `## uds 의견`.

## EXPLORE
- B5: **LA = Saleae Logic 2 자동화 API 1순위**, P2로 앞당김. 스트리밍 불가 제약과 그에 따른 사용자 화면 설계(캡처 중 = Logic 2 앱 + Loom 상태, 캡처 후 = Loom 타임라인·viz·디코드 표)를 정직하게. 시뮬레이션 장치(F4241)와 CI용 자체 Sim 백엔드. sigrok은 2순위.
- B5: PSU는 SimPsu 플러그인 계약 검증 역할만, 실HW는 구매 시. 스코프 보류. 추천 순위 표 갱신.
