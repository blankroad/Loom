# CORE R2 — 교차 리뷰 (둘 다 읽을 것)

상대 워커의 R1 초안을 비판적으로 읽고 리뷰를 쓴다. 한국어. 목적은 리드가 R3에서 `plan.md`로 통합할 때 **어느 쪽을 고를지 근거**를 주는 것이다. 칭찬은 짧게, 틀린 것·빠진 것·더 나은 선택에 집중.

## 입력
- 상대 초안 (아래 개별 지시 참조), 그리고 비교용으로 자기 초안
- 타팀 → CORE 요청 (R1 중에 도착한 것 포함, **전부 확인**): `docs/plan/_xteam/can-core.md`, `uart-core.md`, `uds-core.md`, `core-test.md`(TEST 요청 + core 의견), `core-ui.md`(UI 요구 + core 의견), `test-domains.md`, `ui-test.md`, `ui-panel-template.md`
- `docs/plan/02-core-principle.md` 체크리스트, `00-master-plan.md` §2.3 C1–C8

## 리뷰 형식 (이 순서로)
1. **요약 판정** (5줄 이내): 상대 초안의 가장 강한 점 3개, 가장 큰 문제 3개.
2. **틀린 사실** 표: 위치(절·줄 인용) | 상대 주장 | 실제 | 근거(URL·crate 버전·스파이크 수치·소스 확인 여부 `[확인]`/`[추정]`).
3. **빠진 것** 표: brief 범위 10항목, 02 원칙 체크리스트 6항목, 타팀 요청(파일별 번호 — 예: can-core W1–W10, uart-core 요청 번호, uds-core 번호, TEST TC-C1–C9, UI U1–U8) 중 상대 초안이 답하지 않았거나 잘못 답한 것.
4. **결정 비교** 표 — 두 초안이 다르게 정한 핵심 결정마다: 쟁점 | Opus 안 | Sol 안 | 추천 | 이유. 최소한 다음을 포함: 프로세스 구조(도메인 in-gateway vs worker 판정 기준), worker 전송·직렬화·레인 수, 기록을 worker가 직접 쓰는지(can-core W3), 저널 형식, UI 고속 전송 형식, JSON-RPC 구현(라이브러리 vs 자체), 스키마 생성 도구, 메모리 예산 수치·soak 관문 수치, crate 구조와 P0 stub 범위, CLI 기동 시간 목표, 테스트 세션 증거 검증 방식.
5. **합의 가능한 부분**: 둘이 같은 결론이라 그대로 plan.md에 넣어도 되는 것 목록.
6. **자기 초안 수정 사항**: 상대 초안을 보고 자기 초안에서 틀렸거나 약했다고 인정하는 것 (자기 초안 파일은 수정하지 말고 여기 적기만).
7. **리드에게 남은 사실 확인 질문**: 짧은 확인 작업이 필요한 쟁점 (있으면).

분량: 핵심만, 대략 400행 이하. 사실 주장에는 근거를 붙인다. 필요하면 짧은 추가 스파이크(`spikes/core/` 안)나 문서 확인 가능.

## 규칙
- 쓰기는 자기 리뷰 파일과 `spikes/core/`만. 초안 파일·xteam 파일 수정 금지.
- herdr로 다른 에이전트에게 메시지 금지. 전역 설치·사용자 설정 수정 금지.
- 끝나면 화면에 파일 경로와 3줄 요약만.
