# R4 최종 점검 — can-opus

리드가 R1/R2를 통합해 `docs/plan/can/plan.md`(약 1,030줄)를 썼다. 이를 점검해 `docs/plan/can/r4-check-opus.md`로 보고한다. **plan.md는 직접 수정하지 말 것** (리드가 반영).

## 점검 관점 (Sol은 사실·체크리스트 위주로 따로 점검 중)
1. **핵심 원칙 관점의 사용자/에이전트 경험**: 사용자가 처음 `loom can monitor`를 열었을 때부터 에이전트가 송신하고 사용자가 개입하기까지 흐름에 끊기는 곳이 없는지. M1만 구현됐다고 가정하고 §2.0이 정말 끝까지 돌아가는지(필요한 명령·RPC·TUI 기능이 M1 작업 분해 §12.1에 전부 있는지).
2. **안전 일관성**: §10 등급/승인/lease/STOP 규칙이 §4.3 위험 열, §6.5 설정 예시, §10.9/§15.5 스킬 규칙과 서로 맞는지. 에이전트가 우회할 수 있는 구멍.
3. **아키텍처 일관성**: 2프로세스 결정(§3.1)이 §3.2~3.6, §4.5, §9, §12, §15.2와 모순 없이 반영됐는지 (예: 디코더/SignalCache를 gateway에 둔 것과 wait-for 지연 목표, SimNode 위치, 저널 writer 위치).
4. **스킬 설계**(§15.5): 공통 원칙(viewers 0, NOTE, dry-run) 반영 여부, 90줄 이내로 유지 가능한지, 빠진 규칙.
5. 결정 기록(§16) 중 당신이 강하게 반대하는 것 — 이유와 대안 (짧게).
