## P1 — 반드시 수정

1. **§6.6 명령 표 ↔ §0 불변식 4·§10.3: `raw --expect-*`까지 “모두 R0”로 선언.** `raw 2EF1A002 --expect-resp …`가 쓰기 분류를 우회할 수 있다. 제안: “R0는 읽기 전용 check/wait-for에 한정한다. raw/타입 명령의 기대값 옵션은 실제 바이트의 등급·승인·차단·write_state를 변경하지 않는다.”
2. **§6.6 사전 승인·D29 ↔ §10.4·CORE C-2: 패턴 승인과 구체 요청 결속의 연결이 없다.** 범위 안이라는 검사만으로 bytes/epoch/lease/현재값·정책/DB 해시 결속을 생략할 수 있다. 제안: “부모 승인은 test plan hash·물리 대상·허용 범위·횟수·만료에 결속하고, 매 송신은 실제 바이트와 현 상태로 approval_binding을 생성·검증한다. 범위/등급 상승·상태 변경 시 재승인, 횟수는 원자적으로 소비한다. R3 기본 단계별 viewer, R4 매번 once와 차단 3층은 유지한다.” CORE 계약 확정 전 패턴 승인을 기존 승인 대체로 구현하지 않는다.
3. **§6.6 auto_reconnect·D29 ↔ §3.3–3.4·D19: 링크 회복을 ECU 상태 초기화와 혼동.** TCP 재연결만으로 실제 세션/default·보안/locked를 입증하지 못하며 U 해제 시점도 불명확하다. 제안: “재연결은 기존 세션/보안을 stale로 표시하고 active_overrides를 보존한다(확인된 ECU reset은 별도). DoIP는 구 소켓 응답 원천 폐기와 재활성화 성공 후에만 D19의 해당 U를 해제한다. CAN 채널 재개방·epoch 증가만으로 U를 해제하지 않는다. 미완료 쓰기 outcome_unknown·재전송 금지는 유지한다.”
4. **§6.6·§11 M1·U-29 ↔ §4.1·마스터 A6: 즉시 불일치 exit 3은 아직 미합의 변경.** CORE C-11은 요청 상태이지 확정 계약이 아니다. 제안: “check/단발 --expect 불일치 코드는 CORE 공통 결정 전 미정이며 구현·수용 선행 관문이다. 확정 전 exit 3은 조건 대기 timeout에만 사용하고, ECU 무응답 7·NRC 10과 구분한다.”
5. **§3.8 트랜잭션 링·D31: 대상당 10k 행에는 byte/전역 상한이 없다.** 64대×10k×128 B만으로 약 78 MiB여서 UDS 64 MiB 예산을 넘는다. 제안: “표시 링은 대상당 10k 또는 256 KiB, 전역 8 MiB 중 먼저 닿는 한도로 오래된 표시 행을 회수하고 과거는 저널로 조회한다.” 이벤트 큐도 “CORE 저널 경로”만 적지 말고 포화 시 신규 송신 수용 중단·기록 실패/A12·사용자 예약 경로를 명시한다. 수신/alive는 계속 처리한다.
