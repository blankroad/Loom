# R4 반대 입장 점검 — uds-opus → `plan.md`

**종합: 방향은 맞지만 이대로 M1을 시작하면 E2E-1이 닫히지 않는다.** 원인은 세 가지다: sim 정책, 사용자 origin을 판별할 근거, 승인 패널 범위가 서로 맞지 않는다. 가드에는 우회 경로 3개가 열려 있다(DB 하향, 기능 주소, 자기 신고 origin). 아래 P1 12건을 문서에서 고친 뒤 착수할 것을 권한다.

표기: §n = plan.md 절. "제안"은 대체 문장 또는 작업 ID.

## P1 — 구현 시작 전 반드시 고칠 것

### P1-1. origin을 요청 필드로 받는다 → 사용자 완화 규칙 우회 (§3.6, §10.2, §4.4)
- 문제: `uds.request{…, origin, …}`에서 origin을 클라이언트가 스스로 신고한다. Python API(§4.4)나 임의 RPC 클라이언트가 `origin: "user"`를 보내면 R2 즉시 실행(사용자 완화)이 적용된다. M1 E2E t3(사용자 `2E F1A0 02` 즉시 실행)도 이 완화에 기대는데, 뷰어 자격은 M2(U-17)에 있다.
- 제안 문장(§3.6): "origin은 요청 필드가 아니라 **연결 자격**에서 데몬이 정한다. 일반 RPC 연결 = agent(CLI) 또는 script(Python API), 뷰어 자격 연결 = user. 요청의 origin 필드는 무시하거나 자격과 다르면 거부한다."
- 제안 문장(§10.2): "script origin은 **시나리오 러너 안에서만** 계획 승인 완화를 받는다. Python API 직접 호출은 agent와 같은 규칙(R2 토큰, R3 뷰어)."
- 작업: **U-08a(M1, Opus)** — 뷰어 자격 발급(사용자 완화와 R2 `y`에 필요한 최소분)을 U-17에서 M1로 당긴다. R3 승인 UI만 M2에 남긴다.

### P1-2. 승인 패널이 M1에 있는가 — 세 곳이 다르게 말함 (§1.1, §2.0 t2, §11 M1, U-17)
- §1.1: "M1(승인 패널 제외)". §2.0 t2: "첫 호출 때 하단 승인 패널에 같은 요청이 뜨고 [y]…"(M1 수용 골격). §11 M1에는 승인 패널이 없고, U-17(M2)에 있다.
- 제안: P1-1과 묶어 **M1 = R2 승인 패널 최소판(표시 + `Y` 승인/거부)**, M2 = R3 승인 + 다중 대기 목록 + diff 고급 표시. §1.1을 "M1(R2 승인 최소)", §11 M1 내용에 "R2 승인 패널 최소", U-10 범위에 추가.

### P1-3. sim 대상은 정책상 R0만 허용된다 → E2E t2 쓰기가 exit 4 (§2.0, §10.6, §5.2)
- `unknown_targets: R0`이고 sim 대상의 화이트리스트 항목은 정의되지 않았다. env enum은 `bench|vehicle`인데 §5.2 상태 바에는 `SIM` 배지가 있고, E2E t0 출력은 "policy bench"다.
- 제안 문장(§10.6): "`connect --sim`으로 만든 대상은 **env=sim**으로 자동 화이트리스트(allow_max R3, unlock_r4 금지, 레이트 면제 옵션). env=sim 대상은 데몬이 띄운 가상 엔티티의 주소에만 매칭되며 물리 주소와 절대 매칭되지 않는다." E2E t0 출력을 `policy sim · auto ≤ R1`로 수정.

### P1-4. `--since last`의 "나"가 정의되지 않음 (§4.1, §2.0 t3)
- CLI는 호출마다 새 프로세스다. client id가 프로세스 단위라면 `--since last`는 매번 비어 있고, E2E t3(에이전트가 사용자 개입을 인지)이 동작하지 않는다. `actor_id: claude-1`도 출처가 없다.
- 제안 문장(§4.1): "client id = 환경변수 `LOOM_CLIENT_ID`(없으면 부모 셸 세션 + 사용자 이름으로 만든 안정 id). `loom uds agent-help`와 SKILL.md가 첫 단계로 설정을 안내. 데몬은 client id별 커서를 보관(TTL 24 h)."
- 추가: 모든 결과(사람용 마지막 줄, JSON `others_since_last`)에 "마지막 호출 이후 다른 주체의 트랜잭션 N건"을 붙인다 → 스킬이 매번 `trace`를 부르지 않아도 된다(P2-1).

### P1-5. 진단 DB로 등급을 **낮출 수** 있다 — 가드 우회 (§10.3, §6.4, `db load`)
- "DB 상향만"이라고 했지만 실제 표에서는 하향이 된다. (a) 미등록 RID R3 → DB 등록 시 "DB 등급"(R0도 가능). (b) IO도 DB `risk`가 그대로 적용된다. (c) "DB 없는 쓰기 R3"가 DID를 정의하기만 하면 R2가 된다. 게다가 `db load`는 에이전트가 쓸 수 있는 명령(M1)이고, 에이전트가 YAML을 직접 쓸 수 있다.
- 제안 문장(§10.3): "DB에 적힌 등급은 기본표보다 **낮출 수 없다**. 기본표는 미등록 RID R3, IO 01–03 R3, DB 없는 쓰기 R3다. 하향은 정책 파일(사용자 소유)의 `trusted_db: [sha256…]`에 해시가 등록된 DB만 허용한다. 에이전트의 `db load`는 디코드 용도로만 쓰이고 등급에는 상향만 반영한다."
- 작업: U-02/U-03에 "DB 하향 시도 → 무시 + 감사" 테스트 추가.

### P1-6. 기능 주소 요청이 화이트리스트 밖 ECU에 닿는다 (§10.3, §3.5-5)
- `raw 1101 --functional`이나 `14 FFFFFF` functional은 같은 버스·게이트웨이의 **모든** ECU에 간다. 정책 화이트리스트는 대상(물리 주소) 단위라서 미등록 ECU의 `unknown_targets: R0` 규칙을 우회한다. 등급 +1만으로는 부족하다.
- 제안 문장(§10.6): "R1 이상 기능 주소 요청은 정책의 **전송 범위 항목**(`buses: [{can: ch0, functional_allow_max: R2}]` / `gateways: […]`)이 있어야 하고, 없으면 거부(exit 4). 0x3E·0x22·0x19 기능 주소는 R0로 허용."

### P1-7. timeout 뒤 늦은 응답이 같은 epoch 안의 다음 요청에 붙을 수 있다 (§3.3, §3.4, D2)
- epoch는 재연결 때만 바뀐다. 요청 N이 timeout된 직후 같은 SID/DID로 요청 N+1을 보내면(폴링이 정확히 이 패턴), N의 늦은 응답이 에코 검증을 통과해 N+1의 결과가 된다. UDS에는 요청 id가 없다.
- 제안 문장(§3.4): "timeout 발생 시 대상은 **quarantine** 상태가 된다. 정숙 구간 max(P2*, 정책 `quarantine_ms` 기본 1 s) 동안 새 요청을 보내지 않는다. 그 사이 도착한 응답은 `late` 이벤트로 기록·표시만 한다. 폴링은 quarantine 동안 해당 tick을 skipped로 센다."
- 같은 맥락: 0x2A(주기 응답)와 0x86(이벤트 응답)은 요청 없이 응답이 와서 러너의 1:1 짝짓기를 깨뜨린다. 제안: **러너가 비요청 응답 라우팅을 지원하기 전까지 0x2A/0x86은 R4**(§10.3 표 수정). 현재는 R1/R2라 M1부터 raw로 보낼 수 있다.

### P1-8. D4(자체 DoIP) 관문과 되돌림 경로가 서로 맞지 않음 (§7 끝, D4, U-20)
- §7: "결함 주입 + doip-server 상호운용 관문을 **M1 일정 안에** 넘지 못하면 doipclient로 전환". 그런데 상호운용은 U-20(**M2**)이다. M1 안에 판정할 수 없다.
- 되돌림 대상(doipclient)에는 소켓 공유·LA 분배가 없다(§7 표에 직접 적힘). 되돌리는 순간 "게이트웨이당 소켓 1개 + 다중 ECU"(§3.5-2)를 잃는데 문서에 그 대가가 없다.
- 제안 문장(D4): "M1 관문 = U-05 결함 주입 하위 집합(부분 프레임·coalescing·alive·무응답 deadline). M2 관문 = doip-server 상호운용 + 첫 HIL 스모크. M2 관문 실패 시 되돌림은 'doipclient + 단일 수신 pump 래퍼'이며, 이 경우 **게이트웨이당 동시 대상 1개** 제한을 감수한다(다중 대상은 대상 전환 시 재활성화)." 활성화 응답 0x11(확인 필요)과 OEM 활성화 페이로드(4바이트 OEM 필드)를 결함 주입 목록에 추가.

### P1-9. D16(abort 시 finally 미실행) — 활성 오버라이드가 S3까지 유지됨 (§10.7, D16)
- abort는 "새 송신 없음 → S3 만료로 기본 세션 복귀"에 기댄다. 그러나 0x2F 03(액추에이터 구동)·0x28 disable·0x85 off는 기본 세션으로 돌아갈 때까지(최대 S3, 예 5 s, 프로필에 따라 더 길 수 있음) **계속 유지**된다. 실차에서 문 잠금 모터나 램프가 5초 더 구동되는 것이 abort의 의도와 맞는가? D16에는 되돌림 경로도 없다.
- 제안: TargetSession에 `active_overrides`(IO 대상·제어값, 0x28/0x85 상태, 비기본 세션)를 추적해 상태 바에 표시한다. abort 화면에는 **"복구 송신" 단일 키**를 제공한다(사용자 origin, `2F <id> 00`·`28 00`·`85 01`·`10 01`, 모두 R1). abort 자체는 계속 무송신으로 둔다. D16 이유에 "복구는 사용자 1키, 자동 아님"을 추가. 작업 **U-15a(M2)** + io는 M3라 U-21과 연계.

### P1-10. 승인 키 오조작 위험 + 단축키 충돌 (§5.2, §10.4)
- `y` 한 글자로 승인된다. 패널이 갑자기 뜰 때 사용자가 `:` 명령줄에 입력하던 중이면 `y`가 승인으로 먹을 수 있다. 대기 중인 승인이 여러 개면 `y`가 어느 것에 적용되는지도 정의가 없다.
- 제안 문장(§5.2): "승인은 **패널에 포커스가 있을 때** 대문자 `Y`로만 받는다. R3는 승인 코드 끝 2자를 입력해야 한다. 패널이 나타난 뒤 1 s 동안은 입력을 받지 않는다. 대기 승인이 여럿이면 목록에서 선택한다. 명령줄 입력 중에는 승인 키가 동작하지 않는다."
- 충돌: `[s]top poll`(단축키 줄)과 "`s` 시나리오 패널"(보조 화면)이 같은 키다. 시나리오 패널을 `S`나 `n`으로 옮길 것.

### P1-11. M1–M2 동안 R2의 사람 확인이 스킬 규칙에만 의존 (§10.2, U-25)
- §10.2는 R2 보장 수단으로 (b) `.claude/settings.json` `ask` 규칙을 든다. 하지만 이 규칙은 U-25(**M3**)에 있고, `--confirm`을 가운데 와일드카드로 잡는 패턴 문법이 되는지는 **미확인**(R1에서 표기했는데 plan에서 빠짐). 그러면 기본값 `token_or_viewer`에서 에이전트가 동의 없이 바로 `--confirm`을 붙여도 막을 장치가 없다.
- 제안: (a) `ask` 규칙 작성과 패턴 검증을 **U-12(M1)** 로 당긴다. 패턴이 안 되면 대안으로 `--confirm`을 별도 동사로 분리한다: `loom uds confirm <tok>` → `Bash(loom uds confirm:*)` 접두 규칙으로 `ask`. (b) 검증 전까지 기본값을 env별로 둔다: `sim/bench: token_or_viewer`, `vehicle: viewer`. §10.6 `r2_channel` 주석에 반영.

### P1-12. M1이 기대는 core 산출물과 데몬 수명주기가 작업표에 없음 (§11 선행, §15.4, U-08)
- §11은 "선행: core 데몬 골격·IPC·이벤트 버스·기록기"라고만 적었다. C4는 승인·lease·감사·정책 로더를 **core 공통**으로 요청하는데, U-08은 같은 것을 UDS 안에서 만든다. 누가 만드는지가 겹치거나 빈다.
- 데몬 기동 경로도 없다. 누가 `loomd`를 띄우나(자동 spawn인가 `loom daemon start`인가)? exit 7이면 에이전트는 무엇을 하나? CI는 데몬을 어떻게 띄우나?
- `connect --sim`이 데몬 안에서 가상 엔티티를 띄우고 ephemeral 포트에 바인딩하는 배선을 맡은 작업 ID가 없다(U-05는 모델·어댑터만).
- 제안: **U-00(M1, Opus, 메인 조율)** — core 의존 목록(RPC 라우터·이벤트 버스+seq·기록기·heartbeat·데몬 수명주기·토큰 파일)을 만들고, 각 항목에 "core가 M1까지 못 주면 UDS 모듈 안에 C4 시그니처로 임시 구현 후 이관" 규칙을 둔다. U-05 범위에 "`connect --sim` 데몬 내 기동 + `sim start/stop`"을 추가한다. U-11 의존성에 U-08(안전 수용 (4))을 추가한다. 스킬에 exit 7 분기를 넣는다(P2-1).

## P2 — 개선

### 스킬(§10.9)
- **P2-1 종료 코드 분기를 표로**: 0 → 계속. 1 → 인자 수정, 재시도 1회. 2 → `error.hint`를 사용자에게 보고하고 같은 요청을 반복하지 않음. 3 → `approval.channel`이 `token`이면 사용자 동의 후 `--confirm`, `viewer`면 사용자에게 뷰어 승인을 요청하고 `approval wait`. 4 → 보고하고 우회 금지. 5 → `may_have_executed`면 재전송 금지·보고, 아니면 읽기만 1회. 6 → 사용자에게 제어권 요청. 7 → `loom daemon start`(또는 정해진 기동법) 후 1회.
  - 현재 절차 4는 R2 토큰과 R3 뷰어 승인을 구분하지 않아, 에이전트가 R3에 `--confirm`을 시도하게 된다. JSON에 `approval.channel` 필드를 추가.
- 절차 6("쓰기 전과 매 단계 후 `trace --since last`")은 호출 수를 두 배로 늘린다. P1-4의 `others_since_last`가 0이 아닐 때만 `trace`를 부르도록 바꾼다.
- 절차 4의 "먼저 --dry-run"은 R2+ 첫 호출이 이미 미리보기(exit 3)이므로 중복이다. 문구를 "값을 조립할 때만 dry-run, 실행은 첫 호출이 미리보기"로 바꾼다. E2E t2도 dry-run 없이 진행하므로 지금은 스킬과 E2E가 어긋난다.
- 절차 2: 매번 뷰어를 안내하지 말고 `status`의 `viewers 0`일 때만.
- 금지 추가: "뷰어 패인에 herdr/tmux send-keys 등으로 키를 보내지 말 것(승인·takeover를 대신 누르는 것과 같음)", "`LOOM_CLIENT_ID`를 다른 에이전트 값으로 바꾸지 말 것".

### 안전 세부
- **P2-2 토큰과 상태 결합**: 토큰은 바이트·대상·epoch·lease에 묶여 있다. 그러나 토큰 발급 뒤 다른 주체가 같은 DID를 쓰면, 승인 화면에 보인 diff("00→01")가 거짓이 된다. 같은 DID 쓰기·세션/보안 변화가 생기면 토큰을 무효화(§10.4).
- **P2-3 lease 승계 시 보안 상태**: 에이전트 A가 L1을 해제한 뒤 lease가 만료되면, B가 lease를 잡고 해제 상태를 그대로 이어받는다. 승인 패널에 "보안 해제 주체·시각"을 표시하고, lease 이동 시 상태 바를 경고색으로. 또 승인 대기 중에는 lease TTL을 연장해야 한다(지금은 120 s 대기 중 만료 가능, §3.5).
- **P2-4 stale 세션에서 쓰기**: `session_confidence=stale|assumed`일 때 R2+ 요청은 승인 패널·exit 3 요약에 그 사실을 굵게 표시하고, 스킬은 `status --probe` 선행. 강제 차단까지는 불필요(ECU가 NRC로 막는 경우가 대부분).
- **P2-5 시나리오 동적 값**: `save:` → 다음 단계 `write-did`처럼 ECU 응답에서 온 값이 쓰기 바이트가 되면 계획 시점에 바이트가 미정이다. 계획 승인 1회로 임의 바이트가 허용되면 안 된다. "동적 값은 DB `limits`/`enum` 안이어야 계획 승인에 포함, 아니면 그 단계에서 확인 요구"(§6.5, §10.4).
- **P2-6 suppressPosRsp**: 분류는 `& 0x7F`로 처리하지만 러너 동작이 없다. 제안: "SPRMIB=1이면 P2 동안 NRC만 기다리고, 무응답은 `ok_suppressed`로 기록(timeout 아님)". 0x78은 suppress와 무관하게 올 수 있음.
- **P2-7 env 보정 예외**: "vehicle이면 0x2F 한 단계 상향"이 0x2F 00(returnControl)까지 R2로 올려 복구를 어렵게 만든다. 0x2F 00·0x28 00·0x85 01·0x10 01은 보정에서 제외(§10.2).
- **P2-8 D11 범위**: 활성 ISO-TP tx ID 차단이 **CAN 로그 재생(replay)·주기 송신·IG**에도 적용되는지 명시. 진단 프레임이 섞인 BLF를 재생하면 세션 중간에 요청이 주입된다. CAN 팀 xteam에 "replay/periodic도 같은 차단 또는 해당 ID 필터" 요구 추가. 강건성 시험(의도적 진단 ID 주입)은 "UDS disconnect 후"라는 절차를 D11에 적어 되돌림 경로로 둔다.
- **P2-9 0x2C defineByMemoryAddress(서브 02)**: 이후 0x22로 임의 메모리를 읽는 경로가 된다(0x23과 동일 효과). 등급은 R1 그대로 두되, 동적 DID 범위(F200–F3FF) 0x22를 감사 대상으로 표시.
- **P2-10 뷰어 TTY 확인은 보안 경계가 아님**: 에이전트도 pty를 할당할 수 있다. §10.1 위협 모델 한계에 한 줄 추가.

### 사용자 UX(§5)
- **P2-11 좁은 패인**: §5.2 목업은 약 90열이다. herdr 반쪽 패인(대개 70–80열)용 `--compact` 사양이 목업 없이 한 단어로만 있다. 제안: 대상이 하나면 ecu 열 생략, 시각 `HH:MM:SS.s`, `p2/rtt` 한 열, origin+결과 2글자, 승인은 하단 패널 대신 **전체 화면 모달**. 80열 미만이면 자동 compact.
- **P2-12 이모지 폭**: 🔒🔓⏳⌛⚠⛔은 터미널(특히 Windows conhost, 일부 폰트)에서 폭이 2칸 또는 모호해 열이 밀린다. `--ascii`(L/U/…/T/!/X) 대체와 자동 감지.
- **P2-13 사용자 raw hex 즉시 실행**: 사용자 origin은 R2가 즉시 실행이라 `2E` 오타가 바로 ECU에 쓰인다. 입력 중 실시간 디코드 미리보기 줄(서비스명·DID 이름·등급)을 두고, R2 이상은 Enter를 두 번 누르게 한다.

### 문서 내부 불일치
- **P2-14 마일스톤 의존**: UDS M3 수용 기준에 "CAN-TP 4 KB·FD·기능 그룹 통과"가 있는데, 이는 CAN K9b(**CAN M4**)에 의존한다(§15.4). UDS M3를 CAN M4가 막는다. CAN-TP 전체를 **M3b**(CAN M4 직후)로 분리.
- **P2-15 폴링 레이트**: `per_target_rps: 5`인데 §9.3 고부하 시험은 "5 Hz × 8 DID(벤치 20 Hz)"다. DID별 개별 요청이면 40 req/s로 충돌한다. "폴링 1 tick = 다중 DID 1요청, 레이트 계산은 요청 단위" 명시. 지연 측정 1,000회(§5.4)는 env=sim 레이트 면제가 필요(P1-3).
- **P2-16 lease 표시**: E2E t1 목업이 R0 읽기만 했는데 `lease: agent`로 표시된다(§3.5는 R0에서 lease를 잡지 않음). `lease free`로 수정.
- **P2-17 §4.2 io 등급**: "03 R3, 00 R1"만 있고 01/02가 빠졌다(§10.3은 01/02/03 R3). 맞출 것.
- **P2-18 인용 근거**: §3.5-2의 "AUTOSAR R24-11 SWS_DoIP_00105"는 `spikes/uds/evidence/`에 근거가 없다(검색 확인). 증거를 추가하거나 "추정"으로 표기.
- **P2-19 활성화 타입 0xE0/0xE1(§7 끝 "R4에서 확인")**: 공개 벤더 문서(NI Automotive Diagnostic Command Set, Quantex DoIP 문서)는 **0xE0 = central security**, 0x02–0xDF 예약, 0xE0–0xFF OEM 지정으로 적는다. doipclient의 `CentralSecurity=0xE1`은 틀렸을 가능성이 높다. ISO 원문은 확인하지 못했다. 제안 문장: "0xE0 = central security(벤더 문서 기준, ISO 원문 미확인). doipclient enum 값 0xE1은 인용하지 않는다. CLI는 숫자만 받는다." 근거: [NI DoIP Activate Routing](https://www.ni.com/docs/en-US/bundle/automotive-diagnostic-command-set-toolkit-labview-api-ref/page/doip-activate-routing-vi.html), [NI ndDoIPActivateRouting](https://www.ni.com/docs/en-US/bundle/automotive-diagnostic-command-set-toolkit-c-api-ref/page/nddoipactivaterouting.html), [Quantex ELM327 DoIP](https://quantexlab.com/en/develop/elm327_doip.html).
