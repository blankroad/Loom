# R4 지시 — uds-opus: 반대 입장 점검 (plan.md 수정 금지, 보고서만)

리드가 R3에서 `docs/plan/uds/plan.md`를 통합했다. 당신은 **이 계획으로 구현을 시작하는 팀**이라고 가정하고, 막히거나 위험한 곳을 찾아 `docs/plan/uds/r4-opus-check.md`에 쓴다. plan.md는 직접 고치지 않는다.

## 점검 관점
1. **02 핵심 루프가 M1에서 정말 닫히는가**: §2.0 E2E-1을 §11 M1 범위·§12 U-01~U-12만으로 구현할 수 있는가? 빠진 작업(예: core 의존, 뷰어 자격, 렌더 훅, sim 기동 경로, 데몬 수명주기)이 있으면 지적.
2. **결정 기록 §16의 반대 논증**: 특히 D2(자체 러너), D4(자체 DoIP), D7(승인 채널), D11(raw CAN 차단), D16(abort 시 finally 미실행). 각 결정이 실제로 깨질 수 있는 시나리오와 그때의 되돌림 경로가 문서에 있는지.
3. **안전 구멍**: 가드 우회 경로(Python API, 시나리오 템플릿, 뷰어 명령줄, 기능 주소, 0x2C 동적 DID로 쓰기 우회 등), 승인 토큰 재사용, lease 경합, 세션 stale에서의 쓰기.
4. **스킬 문서(§10.9)가 에이전트를 올바른 순서로 이끄는가**: 짧은지, 모호한 지시, 종료 코드 분기 누락.
5. **사용자 UX**: §5 TUI가 herdr 좁은 패인에서도 쓸 만한가, 승인 패널 흐름이 사람이 실수하기 쉬운지.
6. 문서 내부 모순(수치, 등급, 명령 이름, 마일스톤 번호).

## 출력 형식 (`docs/plan/uds/r4-opus-check.md`)
- 맨 위 종합 1줄. 이어서 P1(구현 시작 전 반드시 고칠 것) / P2(개선) 목록. 각 항목: plan.md 절, 문제, 대체 문장 또는 추가 작업 제안(작업 ID 형태 U-xx).
- 간결하게 (300줄 이내). 파일 쓰기는 `docs/plan/uds/r4-opus-check.md`만.
- 완료 응답: "DONE r4-opus" 한 줄.
