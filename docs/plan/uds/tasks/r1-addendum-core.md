# R1 긴급 추가 지시 (두 워커 공통) — 사용자 재지시, 브리프보다 우선

1. 지금 바로 `docs/plan/02-core-principle.md`를 읽는다. 이 문서는 `00-brief.md`와 UDS 브리프보다 우선한다.
2. 핵심: **에이전트가 장비(ECU, DoIP/CAN-TP)에 직접 접근해 읽고 쓰고, 사용자는 같은 데이터를 같은 순간에 라이브로 본다 (출처 표시, 사용자 개입 가능).**
3. 작성 중인 R1 초안(`docs/plan/uds/r1-opus.md` 또는 `r1-sol.md`)을 이어서 쓰되, 아래를 반드시 포함/수정한다:
   - 문서 맨 앞에 **"핵심 루프" 절**: 직접 접근 / 읽기 / 쓰기 / 사용자 실시간 표시 4요소가 UDS에서 각각 무엇으로 구현되는지 한 표.
   - **종단 간 시나리오 1개 이상**: 예) 에이전트가 `loom uds read-did F190` → ECU가 62 F1 90 ... 응답 → 사용자 트레이스 뷰에 몇 ms 안에 행이 뜸(화면 목업) → 사용자가 뷰어/CLI에서 직접 요청을 보내 개입. 구체적 명령과 화면으로.
   - **실시간성 목표치**: ECU 응답 수신 → 사용자 화면 표시 지연 목표(ms), 그리고 고부하(빠른 DID 폴링, 0x36 대량 전송, 0x78 연속, TesterPresent 반복) 시 화면이 멈추거나 거짓말하지 않는 방법(드롭/집계 표시 명시).
   - **M1 = 걷는 뼈대**: 가상 ECU(시뮬레이션) 위에서 4요소가 최소 형태로 모두 동작. ODX/PDX, 플래시, 멋진 UI 등은 M1 이후.
   - **사용자 화면이 에이전트 세션과 분리되지 않음**: UDS 세션은 상주 프로세스가 소유하고, 사용자가 뷰어를 열면 즉시 같은 트랜잭션 스트림이 보인다. 에이전트 전용 숨은 연결 금지. (예: udsoncan Client를 CLI 프로세스 안에서 직접 열어 ECU와 통신하는 구조는 이 원칙 위반이므로 쓰지 말 것.)
   - 이 원칙에 기여하지 않는 기능은 "후순위" 또는 "비범위"로 명시.
4. 다 쓴 뒤 초안 끝에 "## 핵심 원칙 체크리스트 자가 점검" 절을 넣어 02 문서의 6개 항목 각각에 충족 여부와 해당 절 위치를 적는다.
5. 완료 응답은 원래대로 "DONE r1-opus" / "DONE r1-sol" 한 줄.
